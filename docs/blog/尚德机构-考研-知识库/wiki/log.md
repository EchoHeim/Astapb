## [2026-09-18] research | 「渲染成 HTML 能否保证信息不丢」实测

**动因**：用户提问——不转 Markdown 而改成渲染 HTML，是否能保证内容信息不丢失。

**产出**
- ✨ 新增：[[topics/转换格式方案对比]] —— 三条路线（栅格化 / 定位文字 / 内嵌字体）的确切得失与体积数据
- 实证报告：`_review/html-方案对比.html`（同一页三种做法并排，含失败证据）

**实测数据（4 份代表样本 × 3 页，外推至 7,367 页）**
- 栅格 1.15× → 约 127 MB（是原件 319 MB 的 40%，代价是清晰度与不可搜索）
- 栅格 2.0× → 约 341 MB（**比原件更大**）
- 定位文字 HTML → 约 286 MB（**比原件更大**）
- ⛔ 「渲染成 HTML 省空间」不成立。
- ✅ 但 HTML 对扫描件/整页图片型资料确实优于 Markdown：
  `2022英语考试大纲 p60` 在 Markdown 里是 0 字符，HTML 里是完整整页图。

**关键失败案例（逐层验证）**
- 对象：`12月冲刺学习计划.pdf` p12，原件渲染为「最后一个月，只看重点」
- ① 抽出子集字体：**8 个字体全部无 `cmap` 表**（Identity-H 靠 CID 当字形索引，浏览器走 Unicode 路径）
- ② 合成「码位 = 字形序号」的 cmap 后用 FreeType 逐码位渲染：
  `c=5→们`（应为「最」）、`c=4→什`（应为「后」）→ **码位 ≠ 字形序号**
- ③ 结论：⚠️ **内嵌字体这条路对编码损坏件走不通**。
  正确做法是从 PDF 编码结构重建 CID→Unicode 映射（`pdf2htmlEX` 一类工具的工作），本机无此工具链。
  **该文件只能 OCR 或栅格化。**

**方法论记录（重要）**
- 中途一度得出「内嵌字体可行」的错误结论，原因是只看 `font-family` 与 `@font-face` 名字匹配，
  **没有验证字形是否真的对得上**。补齐验证后推翻。
  **教训：判断「信息有没有丢」不能只看结构，必须端到端渲染出来逐字比对。**

### 项目现状（实测）
- 技术栈：Vite 8 + TypeScript 7，零框架运行时。产物部署到 `/aa/` 子路径，线上 <https://shilong.js.org/aa/>
- 规模：17 个分类 / 97 个站点 / 9 个搜索引擎。有图标 74，首字母色块兜底 23

- 图标全部 256×256，页面以 2rem=28px 渲染 → 面积冗余约 84 倍

工程骨架优秀（构建期硬校验、扁平图标池、防主题闪烁内联脚本、真实 `<a>` 语义、无 innerHTML），
最大短板是图标资源未压缩 —— 占了产物 96%。

### 待办优先级
1. 图标转 64px WebP（预计 2.1 MB → ~150 KB）
2. 折叠卡片键盘可达（当前只有 mouseenter 能展开，被裁的 li 仍在 tab 序里）
3. `dom.ts` 的 `highlight()` 按 token 匹配（现在整串当 single needle，多词搜索不高亮）
4. `#searchHint` 字号 0.6rem = 8.4px，低于可读下限
5. `theme-color` meta 未随手动主题切换
6. `engines.ts` 的 Google 图片 query 缺 `&tbm=isch`

## 布局重构：左侧搜索区 → 顶部居中 + 固定列宽网格

用户要求把左侧搜索区搬到顶部居中，并把每类列宽固定。

### 改了什么
- `index.html`：搜索框包进新的 `.search-row`，Logo 移到输入框之前；`#searchItem` 从 `#search` 外挪进 `#search > div` 内
- `src/styles/layout.css`：整份重写。`#search` 改 `position: sticky; top: 0`（桌面吸顶）；`#grid` 从 flex row wrap 改 `display: grid; grid-template-columns: repeat(auto-fill, var(--col-w)); gap: 1.25rem; justify-content: center`
- `src/styles/tokens.css`：新增 `--col-w: 13rem` 与 `--header-h: 9rem` 兜底；**给暗色主题补上 `--border`**（此前缺失，导致 `border: 0.5px solid var(--border)` 在深色下整条失效）
- `src/styles/components.css`：`.item` 去掉 `margin: 0 1rem`（margin 会吃进固定轨道）；新增 `.site-name` 的 `nowrap + ellipsis`；`.empty` 加 `grid-column: 1 / -1`；`.search-logo` 改绝对定位挂到行外侧；提示文案 `0.6rem → 0.75rem`
- `src/styles/responsive.css`：整份重写。≤650px 时 `--col-w: 10.5rem`、`#search` 放开吸顶（`static`）、主题按钮移到右下角
- **新增 `src/lib/header.ts`**：`ResizeObserver` 量吸顶区真实高度写入 `--header-h`（供 CSS `scroll-margin-top`），并提供 `scrollLine()` 给锚点滚动高亮
- `src/lib/anchors.ts`：判定线从 `innerHeight * 0.25` 改读 `scrollLine()`
- `main.ts`：在 `syncQuery()` 前调用 `observeHeaderHeight()`

### 实测验证数据（CDP 无头 Chrome，1440 与 390 两档）
- 列宽全部一致：桌面 `cardWidths: [182]`（=13rem）、移动 `[147]`（=10.5rem），17 个卡片无一例外
- 搜索框严格居中：`left: 482 / right: 482`（`searchBoxSymmetric: true`）
- 吸顶区高度 161px（桌面），`--header-h` 被正确写入 161.17px
- 引擎图标 1 行、锚点桌面 1 行 / 移动 3 行；长站名桌面 0/97 截断、移动 7/97 截断
- 构建通过：CSS 5.79 kB、JS 22.65 kB

### 踩到的坑
- **`--window-size` 在无头模式下有约 500px 最小宽度限制**，请求 390 实际拿到 500，移动端根本验不了。
  必须走 CDP 的 `Emulation.setDeviceMetricsOverride`。已写了可复用脚本（验证后已删）。
- Logo 参与流内布局会把输入框挤出视口正中约 33px。改成 `position: absolute; right: calc(100% + 0.75rem)` 挂到行外侧，
  并让 `.search-logo` 在 ≤650px 时 `display: none`（否则会跑出可视区外）。
- 深色截图上顶部区域"看起来更亮"，一度以为是背景色写错。用 `getComputedStyle` 验证
  `headerBg === bodyBg === rgb(43,43,43)`，确认是亮色搜索胶囊 + 彩色引擎图标造成的**视觉错觉**，代码无辜。

### 追加调整：去掉吸顶区下方的分割线
用户反馈顶部与内容区之间的那条线要去掉，已从 `#search` 移除 `border-bottom`（`layout.css`）。
暗色主题的 `--border` 变量**保留** —— 右上角主题按钮的圆形描边（`.theme-toggle`）仍在用它。
去掉后顶部与内容区靠搜索胶囊 + 引擎图标的视觉重量自然分层，不需要硬分隔线。

原内容是 `.workbuddy/`，**这会把 `memory/` 一起挡在版本库外**，与仓库根


验证本地视觉验证目录一律加前导斜杠锚定到项目根，避免误伤其它层级同名目录。
改动后 `_shots`、`_backup` 仍被忽略，而 `memory/` 下的 md 重新进入 git 视野。

### 关键技术发现：Windows 上删 Chrome profile 极慢
- **rename 是纯元数据操作**：21 个 profile 目录聚拢耗时 **0.1 秒**
- **删除同样的文件耗时 467 秒**（robocopy /MIR）

同批文件 0.1s vs 467s，证明瓶颈**完全在逐文件 unlink**，不是目录遍历
（本机大概率是 Defender 实时扫描拦截了每次 unlink）。
另外 `--window-size` 那类前台超时会打断删除，而 node 输出到文件是**缓冲**的，
进程被中断就丢缓冲 —— 表现为「命令无输出且退出码 1」，容易误判成脚本报错。

**可复用结论**：以后清理大批碎文件，先 `renameSync` 聚拢到单个 `_trash/` 目录
（瞬间完成、项目立刻恢复干净），再用 `robocopy <空目录> <目标> /MIR` 做原生批量删，
并放**后台**执行。逐文件 `fs.rmSync` 在这种规模下不可用。

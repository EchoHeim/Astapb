# 嵌入式常用通信方式总览：UART、SPI、I²C、CAN、USB、Ethernet 到底怎么选？

> 🐵 程序小猴 · 嵌入式通信协议系列 Vol.00\
> 从一根串口线，到真正的工业网络，我们先把嵌入式通信的地图画出来。

---

做嵌入式开发，迟早都会遇到一个问题：

**两个芯片，怎么把数据传过去？**

MCU 要读取温度传感器，要通信；FPGA 要把检测结果发给
MCU，要通信；设备要把生产数据上传到上位机，还是通信。

于是 UART、SPI、I²C、RS-485、CAN、USB、Ethernet......一个接一个出现。

刚入门时最容易产生一种感觉：

> "它们不都是发 0 和 1 吗？为什么要搞这么多种？"

没错，最后在线路上传输的确实都是信息，但不同通信方式解决的是完全不同的问题。

## 一、先别背协议，先看三个场景

### 场景 1：MCU 读取板上的 EEPROM

距离只有几厘米，数据量不大，而且板上还有 RTC、温度传感器。

这时候 I²C 很舒服：

``` text
MCU
 ├── SDA ───────── EEPROM
 ├── SCL ───────── EEPROM
 │
 ├─────────────── RTC
 └─────────────── Sensor
```

两根信号线就能挂多个设备。

### 场景 2：MCU 和 FPGA 每毫秒交换大量数据

距离还是几厘米，但速度要求明显提高。

这时 SPI 往往更合适：

``` text
MCU                  FPGA
SCLK ───────────────> SCLK
MOSI ───────────────> MOSI
MISO <─────────────── MISO
CS   ───────────────> CS
```

没有地址仲裁那一套复杂流程，时钟拉起来就能快速传。

### 场景 3：控制柜和十几米外的执行机构通信

这时直接拉 TTL UART 就不合适了。

工业现场有电机、变频器、电磁阀，还有长距离线缆带来的干扰。

RS-485 的差分信号开始体现价值：

``` text
控制器                现场设备
  A  ================= A
  B  ================= B
```

同样是"串口数据"，换一个物理层，使用场景就完全不同了。

## 二、常见通信方式放到一张表里

  通信方式         典型特点                   常见场景
  ---------------- -------------------------- ---------------------------
  UART             简单、异步、点对点         调试口、MCU↔FPGA、模块
  RS-232           单端串口物理层             PC、传统仪器
  RS-485           差分、抗干扰、多节点       工业现场、Modbus RTU
  SPI              高速、全双工、线较多       Flash、ADC、FPGA
  I²C              两线、多设备、地址寻址     EEPROM、RTC、传感器
  CAN              多主机、仲裁、错误处理强   汽车、工业控制
  CAN FD           CAN 的高速扩展             新型汽车电子、工业控制
  USB              Host/Device、协议复杂      U盘、PC外设、升级
  Ethernet         高速、网络化               上位机、PLC、服务器
  LIN              低成本、低速               汽车车身电子
  1-Wire           单数据线                   温度、身份识别
  Wi-Fi/BLE/LoRa   无线                       IoT、移动设备、远距离节点

## 三、通信协议其实可以分层看

很多概念混乱，原因是把不同层面的东西放在一起比较。

例如：

**UART 和 RS-485 严格来说不是同一层的概念。**

UART 更接近数据如何按位组织和收发；RS-485主要规定电气传输方式。

一个实际系统可能是：

``` text
应用数据
   ↓
Modbus RTU
   ↓
UART
   ↓
RS-485收发器
   ↓
双绞线
```

所以"UART 和 RS-485 哪个更好"本身就不是特别准确的问题。

更准确的问题应该是：

> 我的数据怎么组织？底层又用什么电气方式传出去？

## 四、选通信方式，重点看什么？

工程里通常关注六件事：

### 1. 距离

PCB 上几厘米和厂房里几十米完全是两个世界。

### 2. 速度

读取一个温度值和传输图像，带宽要求完全不同。

### 3. 节点数量

两个芯片点对点通信很简单；几十个控制器共享总线，就要考虑地址、仲裁和冲突。

### 4. 抗干扰

实验室能跑，不代表装到设备上也能跑。

### 5. 实时性

某些控制数据晚几十毫秒问题不大；某些运动控制数据晚几毫秒就可能出问题。

### 6. 软件复杂度

UART 写几十行代码可能就能收发；USB Host、TCP/IP 则完全是另一个量级。

## 五、一张简单的选型思路

``` text
要通信
 │
 ├─ PCB板内？
 │   ├─ 低速、多器件 ──> I²C
 │   ├─ 高速 ─────────> SPI
 │   └─ 简单点对点 ───> UART
 │
 ├─ 工业现场？
 │   ├─ 简单、便宜 ───> RS-485
 │   ├─ 多节点高可靠 ─> CAN
 │   └─ 高速联网 ─────> Ethernet
 │
 ├─ 连接PC/U盘？
 │   └────────────────> USB
 │
 └─ 不方便布线？
     ├─ 局域高速 ─────> Wi-Fi
     ├─ 低功耗近距离 ─> BLE
     └─ 低速远距离 ───> LoRa
```

这不是绝对规则，但足够作为第一轮筛选。

## 六、真正掌握通信协议，不是背参数

真正有用的能力，是看到通信异常以后知道从哪里查。

比如 UART 出错，你会想到：

-   波特率是不是一致？
-   8N1 还是 8N2？
-   TTL 电平是否匹配？
-   有没有共地？
-   接收是否发生溢出？

RS-485 不稳定，你会继续想到：

-   A/B 是否接反？
-   终端电阻有没有？
-   总线是不是星形布线？
-   收发方向切换是不是太早？
-   共模电压是否超范围？

这才是工程中的"会通信"。

## 先把“接口”和“协议”摆在正确位置

UART 描述异步串行收发形式，TTL/CMOS 电平、RS-232、RS-485 是不同的电气实现；Modbus RTU、自定义帧又是上层报文约定。CAN 已包含仲裁与错误处理，CAN FD 是其帧格式和数据阶段能力的扩展。USB 则还要区分 Host、Device 与设备类。选型时先确定距离、节点、吞吐量、延迟和供电隔离，再决定电气层与帧协议，最后核对芯片外设、布线和调试成本。

以“FPGA 检测结果传给 MCU、MCU 再送到 20 米外控制柜”为例：板内可以用 UART 或 SPI，柜间换成 RS-485 或 CAN；两段链路不必使用同一协议。若要接入局域网和上位机，才进一步考虑 Ethernet 与 TCP/UDP、工业应用协议。

## 写在最后

从这一篇开始，我们会逐个拆开这些通信方式。

下一篇先从最简单、也是几乎所有嵌入式工程师都绕不开的 **UART** 开始。

我们不只讲"UART 是什么"，而是直接看看：

> 当 MCU 发送一个 `0x55` 时，那根 TX 线上究竟发生了什么？

把这一点搞明白，串口通信基本就算真正入门了。

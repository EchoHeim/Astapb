# LIN 总线：汽车已经有 CAN 了，为什么还要再造一个低速协议？

> 🐵 程序小猴 · 嵌入式通信协议系列 Vol.10

---

CAN 很强。

可靠、多节点、仲裁完善。

那汽车为什么还需要 LIN？

答案很现实：

> 不是所有节点都值得用一套昂贵的 CAN 硬件。

比如车窗、座椅、后视镜、简单执行器，它们的数据量并不大。

## 一、LIN 的目标就是低成本

LIN 通常采用单线通信。

相比 CAN 的双线差分和专用控制器要求，LIN 节点可以做得更便宜。

典型结构：

``` text
          ┌── Slave
Master ───┼── Slave
          ├── Slave
          └── Slave
```

## 二、LIN 更像"班主任点名"

CAN 节点可以参与总线仲裁。

LIN 则通常由 Master 决定通信节奏。

Master：

> "3号节点，该你发了。"

Slave 3 才响应。

这样系统简单很多。

## 三、LIN 帧大概是什么样？

可以粗略看成：

``` text
Break
 ↓
Sync
 ↓
Identifier
 ↓
Data
 ↓
Checksum
```

其中 Sync 可以帮助从节点同步波特率。

## 四、为什么速度不高？

LIN 本来就不是为了高速。

它更关注：

``` text
低成本
简单
够用
```

典型速率上限大约在 20kbps 级别。

用它传摄像头数据当然不合适。

控制车窗状态却完全够用。

## 五、CAN + LIN 是互补关系

可以想象成：

``` text
        CAN Backbone
      /      |       \
    ECU     ECU      ECU
             |
            LIN
          /  |  \
       Window Seat Mirror
```

CAN 做骨干。

LIN 做低成本末端网络。

这是一种很典型的系统工程思维：

> 不让所有节点都使用最高规格的通信方案。

---

## 为什么车门上的节点不用全上 CAN？

LIN 常用于成本和带宽要求都较低的车身节点，由主节点安排通信时刻。典型帧由主节点发出 break、同步字段 `0x55` 和标识符，随后由指定发布者提供数据与校验。它适合按计划上报开关或执行器状态；如果系统需要多主仲裁和更高可靠性，应重新评估 CAN。

排查 LIN 时先看主节点是否按计划发送帧头，再查标识符、波特率同步、发布者和校验配置。不要把 LIN 的单线物理接口直接接到普通 MCU UART 引脚上，仍需符合其电气要求的收发器。

## 写在最后

LIN 给嵌入式开发一个很好的提醒：

**技术选型不是参数越高越好。**

满足需求以后，成本、复杂度和可靠性同样重要。

下一篇更加极端：

**如果连两根信号线都嫌多，能不能只用一根？**

答案就是 1-Wire。

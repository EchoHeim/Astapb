# 金句库

开头钩子、结尾金句、以及「小猴点评」的口吻模板。
**金句的作用不是显得有文采，是把读者按在屏幕前别划走。**

## 一、开头钩子（正文前 3 行）

正文第一段必须在 **3 行内给出结论或冲突**。以下句式可以直接套：

**现象冲击型**
- 「这块板子我调了三天，最后发现是配置文件里多了一个空格。」
- 「服务内存每天涨 2%，重启能好，但谁都知道这不是办法。」

**代价前置型**
- 「为了省 30 秒的挂载操作，我花了一个下午写 udev 规则——现在想想是值的。」
- 「这个 bug 让我加班到凌晨两点，根因是一个 sizeof。」

**结论前置型**
- 「先说结论：<补结论>。下面是完整的排查过程。」
- 「这个问题不用改代码就能解决，关键在一行 udev 规则。」

**避坑清单型**
- 「如果你也遇到了 <现象>，先别急着改代码，按顺序排查这 5 个地方。」

**反常识型**
- 「网上都说要加 virtual，但真正的原因不是多态，是内存释放。」

### 反例（不要再写）

| 别写 | 为什么 |
| --- | --- |
| 「最近在整理 Linux 的笔记，顺便分享出来」 | 没有任何理由让读者继续读 |
| 「本文主要介绍 xxx 的相关内容」 | 像论文摘要，不像人在说话 |
| 「众所周知，xxx 是一个很重要的东西」 | 空转，浪费了最贵的位置 |

**另外：正文首屏不要放图片。** 图片会挤占折叠区前的高度，把钩子推到「展开全文」之后。

## 二、「小猴点评」口吻模板

这是「程序小猴」最核心的差异化资产，日报里每一条都要有。四条规则：

1. **不复述新闻，只给判断。** 新闻本身读者已经看到了。
2. **给一个连带的推论。** 「这说明……」——把孤立事件接到更大的趋势上。
3. **对开发者说一句有用的。** 让读者能带走一个动作或判断依据。
4. **允许有立场，但说清依据。** 不做和事佬，也不要空喊。

### 句式模板

| 模板 | 适用 |
| --- | --- |
| 「<主体>不是简单的<表面动作>，而是一次<更本质的事>。<数字>说明<结论>。」 | 重大发布类 |
| 「这<条新闻>对多数人可能不太性感，但信息量巨大。第一……第二……做<某方向>的同学，<可执行建议>。」 | 看似平淡但重要的 |
| 「<现象>，翻译一下就是：<大白话>。更值得关注的是<次要信号>。」 | 需要祛魅的 |
| 「这场<事件>最有价值的不是<表象>，而是<真正的共识>。做<某方向>的，与其<错的做法>，不如<对的做法>。」 | 论坛/观点类 |

### 真实范例（来自 9 月 19 日日报，可直接参考语气）

> 昇腾960不是简单的芯片升级，而是一次系统级「亮剑」。11颗超节点芯片全栈自研、NPO光引擎
> 替代4.8万颗传统光模块、功耗直降550千瓦——这些数字说明华为的打法已经从「单芯片追赶」
> 转向「系统架构碾压」。

> 黄仁勋说「明年翻倍」，翻译一下就是：英伟达的订单簿已经排到2028年了。

> 这条新闻对大多数开发者来说可能不太「性感」，但信息量巨大。第一，AMD在AI推理市场已经
> 不是陪跑者了……第二，「AI网关按任务分发到不同模型」这个架构思路很值得学习。

## 三、结尾金句

结尾不要「以上就是全部内容，感谢阅读」。二选一：

**留一个具体问题**（推动评论）→ 见 `固定模块.md` 的互动话术
**留一个可执行的下一步**（推动收藏转发）
- 「如果你也在踩这个坑，把这段配置直接抄走就行。」
- 「下次遇到网卡起不来，先别怀疑驱动，按上面的顺序读一遍 PHY 寄存器。」

---

## 四、积累方式

每次写稿遇到一句自己觉得「说得挺准」的话，**立刻复制到这里**，并标注来源文章。
用满 50 句之后，写新稿时先翻一遍——大部分开头都不用重新构思。

> 「小猴点评」属于二次创作。引用新闻事实时必须在文中保留来源与「仅代表个人观点」的声明，
> 且原创点评的篇幅应占到该条内容的一半以上。

# 根分区满了报 No space left on device，不重装系统的扩容全过程

🐵 **程序小猴 · 实用软件分享**

编译到一半，屏幕上跳出一行。

```text
No space left on device
```

这是我在一台板子上遇到的情况。根分区 8 G，塞满。

第一反应是想重刷系统。可那台机器上跑着一堆调好的环境，交叉编译链、依赖库、配置文件，重刷就得从头再来一遍，保守估计一整天。

后来发现不用。数据还在，改一下分区表就行。整个过程十分钟，风险点只有一处，我下面单独标出来。

---

## 先确认是真不够，还是有垃圾

扩容之前花一分钟看看空间被谁吃了。

```bash
du -sh /* 2>/dev/null | sort -h
```

这条会把根目录下每个子目录的大小列出来，从大到小排。我遇到过三种常见情况。

日志把 `/var/log` 撑爆，这种清掉就好，不用扩容。Docker 的镜像和容器堆在 `/var/lib/docker`，`docker system prune` 能回收一大块。还有就是编译产物，比如 build 目录、下载的源码包，删掉立刻见效。

我那次是把这三种都试过了，才腾出不到 1 G。确认留不住，再往下走。

---

## 三条路，先判断你属于哪种

根分区扩容有三条路，选错工具会白折腾。先按这张表定位。

| 你的情况 | 走哪条路 | 用什么 |
| --- | --- | --- |
| 官方系统镜像烧的卡（Raspberry Pi OS 等） | 官方工具，最省事 | `raspi-config` |
| 自己分的区，或用的是普通 MBR/GPT 分区表 | 改分区表 + 扩文件系统 | `fdisk` + `resize2fs` |
| 用了 LVM（逻辑卷） | 扩逻辑卷，不碰分区表 | `pvcreate` / `vgextend` / `lvextend` |

**先判断有没有用 LVM**，敲这三个命令，任何一条有输出就说明在用。

```bash
pvdisplay   # 物理卷
vgdisplay   # 卷组
lvdisplay   # 逻辑卷
```

都报「not found」或者什么都没有，说明不是 LVM，走中间那条。**本文主要讲中间这条**，它覆盖的场景最多，也最容易踩坑。

LVM 那条更安全但步骤更长，放在文末说。

---

## 动手之前先看两眼

先看现在用了多少，以及是什么文件系统。

```bash
df -Th
```

`-T` 会带上文件系统类型，**这一步不能省**。后面用的扩容命令和它直接相关，ext 系列和 xfs 用的不是一个东西，名字搞错就是白跑一趟。

再看整块盘的分配情况。

```bash
lsblk
```

我那台机器上 `mmcblk1` 一共 20 G 出头，根分区只占了 8 G，剩下 12.5 G 一直空着没用。看到这个数字心里就有底了。盘本身是够的，只是没划给它。

顺手跑一次文件系统检查，确认没有错误。

```bash
sudo e2fsck -f /dev/mmcblk1p1
```

这一步可以跳过。但磁盘上如果本来就有错，后面扩容会出一些很奇怪的问题，排查起来比重跑一次麻烦得多。

---

## ⚠️ 唯一的风险点

下面要用 fdisk **删掉根分区再重建**。

听起来很吓人，但**删分区不会动数据**。它改的只是分区表里那条记录，也就是「这块地从哪到哪」。真正的数据在扇区里，fdisk 不碰。

致命的是另一件事。

**重建时，起始扇区必须和原来一模一样。**

填错一位，文件系统就找不着自己的开头，数据等于全丢。所以进 fdisk 之后第一件事，是把当前根分区的起始扇区抄下来。截图、拍照、抄纸上，怎么都行，**别靠脑子记**。

我当时的做法是手机拍一张，然后每一步都对一眼。

---

## 改分区表

进 fdisk。

```bash
sudo fdisk /dev/mmcblk1
```

按 `p` 打印分区表，记下根分区的**起始扇区**。

按 `d` 删除根分区。

**这时候千万别按 `w`。** 一保存就真没了，后面还要靠原来的起始位置重建。

接着按 `n` 新建分区。起始扇区填刚才抄下来的那个数字，结束扇区直接回车用默认值，也就是把剩下的空间全吃掉。

确认无误后按 `w` 保存退出。

让内核重新读一次分区表。

```bash
sudo partprobe /dev/mmcblk1
```

提示设备忙的话就重启一次，效果一样。

---

## 让文件系统跟着变大

分区表改完，`lsblk` 里看到的容量已经变了，但 `df -h` 还是老样子。分区变大了，文件系统还不知道。

ext2/3/4 用这条。

```bash
sudo resize2fs /dev/mmcblk1p1
```

xfs 不一样，要用 `xfs_growfs`，参数是**挂载点**，不是设备名。

```bash
sudo xfs_growfs /
```

跑完再 `df -h`，容量就对上了。我那台 8 G 的板子变成了 20 G，编译接着往下跑，没再报错。

整个过程里让人心跳加速的，只有填起始扇区那一下。

---

## 为什么 df 和 lsblk 对不上

这是扩容中途最容易让人慌的一件事。改完分区表，`lsblk` 显示 20 G，`df -h` 还写着 8 G。

两个命令都没错，它们看的不是同一个东西。

| 命令 | 看的是什么 | 扩容后什么时候变 |
| --- | --- | --- |
| `lsblk` | 分区表——这块地划了多大 | 改完分区表立刻变 |
| `df -h` | 文件系统——这块地上盖了多少能用的房子 | 跑完 `resize2fs` 才变 |

中间差的那一步，就是 `resize2fs`。

所以顺序不能反。**先扩分区，再扩文件系统**。反过来做，`resize2fs` 会告诉你「没有空间可以扩」。

还有个常见报错。跑 `resize2fs` 时提示要先 `e2fsck`，照做就行。那是文件系统自己要求先体检一次。

---

## 扩容之后验一下

```bash
df -h /
lsblk
```

两个数字对得上就稳了。我一般会再随便写个文件进去，确认真的可写。

```bash
dd if=/dev/zero of=/tmp/test bs=1M count=100
rm /tmp/test
```

能写进去再删掉，比只盯着数字踏实。

---

## 三个容易忽略的前提

**一、盘超过 2 TB 的话，检查分区表格式。** MBR 最多四个主分区，单个分区不能超过 2 TB，工具是 `fdisk`。GPT 没这些限制，工具换成 `parted`。2 TB 以上的盘别用 MBR，不然后面怎么扩都过不去。

**二、LVM 的路子更长，但更安全。** 思路是新建物理分区，转成物理卷，加进卷组，最后扩展逻辑卷。命令依次是 `pvcreate`、`vgextend`、`lvextend`，收尾同样要 `resize2fs`。它的好处是可以在线扩，不用删分区，风险比改分区表低。如果这台机器以后还要扩，值得一开始就用 LVM。

**三、动分区表之前能备份就备份。**

上面所有命令我都跑通了，但你的盘和我的不一样。分区表这种东西，出错一次就够后悔很久。

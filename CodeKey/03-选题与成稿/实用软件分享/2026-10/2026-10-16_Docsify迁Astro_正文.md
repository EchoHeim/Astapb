# Docsify 迁到 Astro，247 MB 降到 11 MB，文章终于能被搜到

🐵 **程序小猴 · 实用软件分享**

真正让我下决心换掉 Docsify 的，不是体积。

是有一次我想找自己写过的一篇笔记。在博客的搜索框里敲了关键词，什么都没有。

那篇文章确实在站上，我记得清清楚楚写过。后来才发现，Docsify 的搜索只索引侧边栏里出现过的链接，我那四十多篇压根没被收进去。

自己写的文章自己搜不到，这件事比「站点有点慢」难受多了。

---

## 当初为什么选 Docsify

公平地说，它有个特别爽的地方。

丢一个 Markdown 进去就能渲染，不用构建，不用装依赖，改完刷新页面就看到效果。写笔记这件事上几乎零成本，我那几年攒下来的一百多篇文章，全都是这么丢进去的。

代价是它把渲染放到了浏览器端。页面加载时先把 Markdown 拉下来，再由前端脚本现解析成 HTML。这套机制决定了后面所有问题。

---

## 老站的四根刺

| 问题 | 具体表现 |
| --- | --- |
| **搜索只认侧边栏** | 正文不进索引。文章越多，这个洞越大，四十多篇在站内搜不到 |
| **URL 带 `#`** | 用的是 hash 路由，地址长这样：`https://shilong.js.org/#/blog/xxx` |
| **每页 title 都一样** | `<meta name="description">` 里填的是模板占位符，就算被收录，摘要也是重复的 |
| **首屏拉十几个外链** | 其中有 CDN 已经停止维护，一抽风页面就白 |

第三和第四条是我后来才发现的，前两条才是根子。

搜索引擎基本不看 `#` 后面的内容。站上所有文章，对搜索引擎来说约等于不存在。我后来去搜自己的文章标题，一条都搜不出来。写了几年，等于写在一个只有我自己知道的地方。

---

## 换成 Astro 之后

新站在 2026-09-18 那天接管了根路径。先把数字摆出来，这些是迁移前后最直观的差别。

| 指标 | 老站（Docsify） | 新站（Astro） |
| --- | --- | --- |
| 部署产物 | **247 MB** | **11 MB**（gzip 后 1.55 MB） |
| 首屏需要下载 | 十几个外链脚本 | **约 11.7 KB** |
| 渲染方式 | 浏览器端解析 Markdown | 构建时生成纯 HTML |
| 页面 URL | `/#/blog/xxx` | `/blog/xxx` |
| 搜索范围 | 只索引侧边栏链接 | **标题 + 标签 + 正文全量索引** |
| 每页 meta | 全站共用一行占位符 | 独立 title / description / canonical / OG |

顺手把 Docsify 那一整套机制删了，105 个文件、约 14 MB。现在站上只剩文章源、图片和站点代码，没有第二套渲染体系。

前面那四根刺，一根一根拔掉了。

搜索改成构建时生成全量索引，那四十多篇终于能搜到。URL 换成真实路径，每篇一个地址，能被收录。每页有独立的 title、description、canonical 和 OG 标签，不再是全站共用一行占位符。

还补上了 RSS 和 sitemap，加了亮暗双主题，能跟随系统，也记得住手动选的那个。

现在整站构建出来是一百多个静态页面，全部是纯 HTML，没有前端渲染这一步。

---

## 迁移不是一键的事

这部分我想说得实在点，因为网上的迁移文多半只讲好处。

最大的一次折腾跟内容目录有关。整合的时候内容目录被挪了两次，从 `docs/blog/` 挪到 `WebBlog/blog/`，最后才落到 `WebBlog/docs/`。

每挪一次，下面这几处都得跟着改，漏一处就出事。

```text
src/content.config.ts          的 base
scripts/sync-content.mjs       的 BLOG 和它的 git 前缀剥离规则
scripts/migrate-assets.mjs     的 BLOG
```

光是「改个目录名」这个动作，就把配置、脚本和 CI 全牵了一遍。如果你也要动内容目录，先把这三处记下来。

第二件体力活是 frontmatter。老站的 Markdown 没有 frontmatter，tags 覆盖率是 0。迁过来之后要一篇一篇补标签、日期、摘要，文章多的话纯靠手。

第三件是图片。老文章里的图片路径是另一套规则，得写脚本批量搬，顺带把引用地址一起改掉，否则页面全是裂图。

---

## 现在发一篇文章要走几步

这是迁移之后我最满意的地方。

往 `docs/<分类>/` 里丢一个 Markdown，git 提交，推送，GitHub Actions 自己构建、自己部署，几分钟后线上就有了。整站一百多个页面全部重新生成一遍，不用我管。

代价也很明确，得说清楚。

本地要装 Node 环境，改一个错别字也得跑一次构建才能预览，不像 Docsify 那样改完刷新就看到。构建本身要几分钟，文章越多越久。还有前面提过的那些配置路径，动了内容目录就得同步改三处。

| | Docsify | Astro |
| --- | --- | --- |
| 写一篇的成本 | 丢文件，刷新就看 | 丢文件，提交，等构建 |
| 改一个错别字 | 刷新即可 | 等几分钟构建 |
| 本地环境 | 不需要 | 要 Node |
| 能不能被搜到 | **不能** | 能 |

这些麻烦换来的东西，是文章能被搜到。我觉得值，但这个账每个人算出来不一样。

---

## 什么情况下别折腾

如果你的站只是给自己当笔记看，不指望被搜到，Docsify 够用。丢一个 Markdown 进去就能渲染，这个便利性是真的，我现在写临时文档还在用它。

但如果你想让人搜到你写的东西，hash 路由这一条就是硬伤。搜索引擎进不来，写得再多也只有自己看。

我是在想明白这件事之后才动手的。体积从 247 MB 掉到 11 MB 是顺带的，真正值钱的是那四十多篇终于能被搜到。

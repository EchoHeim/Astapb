# CAN FD：经典 CAN 不够用了，然后工程师把它"加速"了

> 🐵 程序小猴 · 嵌入式通信协议系列 Vol.07

---

经典 CAN 很可靠。

但随着汽车电子和工业控制数据越来越多，一个问题越来越明显：

**8 Byte 一帧，真的有点挤。**

于是 CAN FD 出现了。

FD 是 Flexible Data-rate。

名字已经说出了两个重点：

**数据更多，数据阶段还能更快。**

## 一、经典 CAN 的两个限制

经典 CAN：

``` text
单帧数据最多 8 Byte
```

而且整帧基本按照同一个位速率运行。

当数据量增加时，效率开始成为瓶颈。

## 二、CAN FD 一帧可以带更多数据

CAN FD 数据字段最大可以扩展到：

``` text
64 Byte
```

于是原来需要多帧发送的数据，可能一帧就能完成。

## 三、真正有意思的是"变速"

CAN FD 可以：

``` text
仲裁阶段：较低速率
数据阶段：更高速率
```

为什么不从头到尾都高速？

因为仲裁阶段涉及多个节点共同竞争，需要考虑整个总线传播延迟。

进入数据阶段后，只剩当前获胜节点发送，就有机会提高速率。

## 四、BRS 是什么？

BRS：

**Bit Rate Switch**

用于表示数据阶段是否切换到更高位速率。

所以 CAN FD 配置时经常会看到两套时序参数：

``` text
Nominal Bit Timing
Data Bit Timing
```

这也是 CAN FD 调试比经典 CAN 多出来的一层复杂度。

## 五、CAN FD 不是"换个配置就一定能用"

首先硬件必须支持。

包括：

-   CAN 控制器；
-   CAN 收发器；
-   网络中的其他节点；
-   分析仪。

经典 CAN 节点看到 CAN FD 帧时，兼容性必须根据具体网络设计考虑。

## 六、速率提高以后，物理层要求更严格

同一条线：

``` text
500 kbps 能跑
```

不意味着：

``` text
2 Mbps / 5 Mbps 数据阶段
```

也一定稳定。

速率越高，对以下因素越敏感：

-   总线长度；
-   支线长度；
-   终端匹配；
-   收发器性能；
-   PCB；
-   线束；
-   时钟误差。

## 七、什么时候值得使用 CAN FD？

当你需要：

-   保留 CAN 的可靠性；
-   更高吞吐量；
-   更大的单帧 Payload；
-   更现代的汽车/工业网络；

CAN FD 很有吸引力。

如果系统只有几个字节状态量，经典 CAN 可能已经完全够用。

---

## 一帧变长之后，调试思路也要跟着变

CAN FD 可将单帧数据段扩展到最多 64 字节，并可通过 BRS 在数据阶段使用更高比特率；仲裁阶段仍采用适合全网共同识别的标称速率。不是所有 CAN FD 帧都必须加速，BRS 可以关闭。系统必须同时核对控制器、收发器和分析仪是否支持 FD，以及标称阶段和数据阶段两套位时序。

举例：旧节点只支持经典 CAN，直接把 FD 帧放入同一总线，可能触发错误，不能仅靠修改新节点固件解决。升级项目应先盘点所有节点能力与网关方案；调试时分别记录 FDF、BRS、DLC、实际数据长度和错误帧，别把 DLC 当成所有情况下都等于字节数。

## 写在最后

CAN FD 并没有推翻 CAN。

它更像是在保留 CAN
核心机制的基础上，把"货车车厢"加大，同时允许部分路段跑得更快。

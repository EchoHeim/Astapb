# CAN 总线详解：几十个控制器同时在线，为什么不会乱成一锅粥？

> 🐵 程序小猴 · 嵌入式通信协议系列 Vol.06

---

一辆汽车里可能有大量 ECU。

发动机、车身、仪表、空调、门窗......

如果每两个控制器之间都单独拉 UART：

线束大概会先疯掉。

CAN 的思路是：

> 大家挂在同一条总线上，需要说话时自己发。

问题来了：

**两个人同时说怎么办？**

CAN 最精彩的地方就在这里。

## 一、CAN 使用差分信号

典型总线：

``` text
120Ω                               120Ω
 |                                   |
CAN_H ============================== CAN_H
CAN_L ============================== CAN_L
       │          │          │
      ECU1       ECU2       ECU3
```

两端通常配置终端电阻。

## 二、CAN 不是传统"设备地址"思路

CAN 帧里的 Identifier 更接近：

> 这条消息是什么？

而不是：

> 这条消息发给谁？

例如：

``` text
0x101 = 电机转速
0x120 = 温度
0x201 = 控制命令
```

所有节点都可以看到总线消息，再通过过滤器决定自己关心哪些 ID。

## 三、两个节点同时发送怎么办？

CAN 使用位仲裁。

简单理解：

``` text
显性位 0
隐性位 1
```

如果某节点发送 1，却在总线上读到 0：

> 它知道有优先级更高的节点正在发送。

于是主动退出竞争。

这个过程不会像传统冲突那样把整帧数据撞坏。

## 四、为什么 ID 越小通常优先级越高？

仲裁从 Identifier 高位开始逐 bit 比较。

因为显性 0 会覆盖隐性 1，所以在标准仲裁机制下，数值较小的 ID
通常能继续占据总线。

因此 CAN ID 的规划，本身就包含实时系统的优先级设计。

## 五、CAN 为什么可靠？

它内置了大量错误检测机制，例如：

-   CRC；
-   ACK；
-   位监测；
-   格式检查；
-   填充规则检查；
-   错误计数；
-   错误主动/被动状态；
-   Bus-Off。

也就是说 CAN 控制器不仅会"发数据"，还会持续判断：

> 我自己是不是已经不太正常了？

严重异常的节点甚至会退出总线，避免一直干扰其他设备。

## 六、CAN 帧里有什么？

经典 CAN 数据帧可以粗略理解为：

``` text
SOF
 ↓
Identifier
 ↓
Control
 ↓
Data
 ↓
CRC
 ↓
ACK
 ↓
EOF
```

经典 CAN 单帧数据字段最多 8 Byte。

对于现代系统，这也是后来 CAN FD 出现的重要原因之一。

## 七、CAN 最容易忽略的是终端和拓扑

CAN 不是"把 CAN_H/CAN_L 接起来就行"。

需要关注：

-   两端终端电阻；
-   支线长度；
-   总线拓扑；
-   波特率；
-   共模范围；
-   收发器供电；
-   隔离与防护。

很多所谓"软件 CAN 问题"，最后拿示波器一看，是波形已经严重变形。

## 八、调试 CAN 推荐看什么？

除了协议分析仪，还建议看：

``` text
CAN_H
CAN_L
```

进一步观察差分：

``` text
CAN_H - CAN_L
```

软件侧则关注：

-   TEC；
-   REC；
-   Error Passive；
-   Bus-Off；
-   ACK Error；
-   Stuff Error。

这些状态比一句"CAN 收不到"有价值得多。

## 工程实战：看懂一帧和一次仲裁

两个节点同时发送标准帧，ID 分别为 `0x100` 和 `0x080`。仲裁区逐位比较，发送隐性位却读回显性位的一方停止发送；优先级由 ID 的首个不同位决定，因此**数值较小的 ID 通常先赢**。这是总线层仲裁，不是软件队列“谁先调用发送函数”。CAN 标识符表达报文含义或优先级，设备地址属于系统设计选择。

经典 CAN 数据帧最多 8 字节载荷，实际带宽还包含 SOF、仲裁、控制、CRC、ACK、EOF 及位填充。估算总线负载时，不能只拿 `8 字节 × 帧率` 去除以标称速率。调试首先核对全部节点的标称比特率与采样点，再检查两端终端、共地/隔离设计、收发器使能、ACK 和错误计数。只有一台节点接在线上时，它可能因无人应答而重复发送，即使示波器能看到电平活动也不代表通信成功。

抓包记录时间戳、ID、DLC、数据、错误帧与总线负载；若某个高优先级报文频繁出现，低优先级消息可能延迟，需要按最坏时延而非平均带宽评估控制链路。

## 写在最后

CAN 真正厉害的地方，不只是差分传输。

而是它把：

**多节点竞争、优先级仲裁、错误检测、故障隔离**

都考虑进了协议。

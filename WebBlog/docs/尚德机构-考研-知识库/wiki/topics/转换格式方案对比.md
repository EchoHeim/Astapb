# 转换格式方案对比：Markdown vs 渲染 HTML

**结论速览**：把资料渲染成 HTML **不能保证信息不丢**。
它比 Markdown 多保住的是**图形与版式**，代价是**体积**（与原件相当甚至更大）与**可搜索性**；
而**字符编码已经损坏的文件，HTML 同样救不了**——这一点经实测验证。
本页记录实测数据与三条路线的确切得失。

---

## 一、先分清：「渲染成 HTML」有三种完全不同的做法

| 路线 | 做法 | 视觉 | 文字可搜索 | 依赖本机字体 | 体积 |
| --- | --- | --- | --- | --- | --- |
| **A 栅格化** | 每页渲染成 JPEG，塞进 HTML 的 `<img>` | ✅ 与原件一致 | ❌ 变成像素 | — | 中 |
| **B 定位文字** | `PyMuPDF` 的 `get_text("html")`：真实文字绝对定位 + 内嵌图片 | ✅ 多数情况 | ✅ 真实字符 | ⚠️ **是**（只写字体名） | 小～大 |
| **C B + 内嵌字体** | 在 B 基础上把 PDF 的子集字体抽出来注入 `@font-face` | 预期 ✅ | ✅ | ❌ 不依赖 | 略大 |

> `pdf2htmlEX` / `mutool` 是这条路线的专业工具（会重建 CID→Unicode 映射），
> 但**本机没有**，实测全部走 Python 方案。

---

## 二、体积实测（单页均值，样本 4 份 × 3 页）

| 类型 | 栅格 1.15× | 栅格 2.0× | 定位文字 HTML | 原件 |
| --- | --- | --- | --- | --- |
| 文字型（逻辑真题） | 70.2 KB | 197.8 KB | **11.0 KB** | — |
| 幻灯片（写作课件） | 43.2 KB | 110.2 KB | 166.1 KB | — |
| 扫描件（英语考纲） | 19.8 KB | 56.0 KB | 129.8 KB | — |
| 公式表格（密训数学） | 79.0 KB | 204.0 KB | 169.9 KB | — |
| **全库外推（7,367 页）** | **约 127 MB** | **约 341 MB** | **约 286 MB** | **319 MB** |

**读法**：
- 只有**低分辨率栅格**能把全库压到 127 MB（是原件的 40%），代价是清晰度损失、文字不可搜索。
- 栅格 2.0×（约 144 dpi）与定位文字 HTML **都比原件更大**。
- **「渲染成 HTML 省空间」是不成立的。**

## 三、HTML 真正胜过 Markdown 的地方

对**扫描件 / 整页图片型**资料，Markdown 里什么都没有，而 HTML 会把整页图片内嵌进去：

| 样本 | Markdown | HTML（定位文字路线） |
| --- | --- | --- |
| 2022 英语考试大纲 p60（扫描件） | **0 字符** | 整页 JPEG 内嵌，**视觉完整** |
| 中文写作课件 p6（幻灯片） | **11 字符** | 1920×1080 底图 + 5 张子图 + 少量真实文字 |
| 密训数学 p3（公式表格） | 文字在但**公式运算符丢失** | 整页底图 + 214 个真实文字，**两者都在** |

所以 HTML 是更好的**保真呈现层**；Markdown 是更好的**检索层**。二者互补，不能互相替代。

---

## 四、HTML 救不了什么（实测证据）

### 4.1 字符编码损坏的文件 —— 内嵌字体也不行

以 `12月冲刺学习计划.pdf` 第 12 页为例，逐层验证：

| 步骤 | 观察 | 结论 |
| --- | --- | --- |
| ① 原件渲染 | 正常显示「**最后一个月，只看重点**」 | 字形都在，只是**编码**坏了 |
| ② 抽出子集字体 | 8 个字体**全部没有 `cmap` 表**（只有 `cvt fpgm glyf head hhea hmtx loca maxp prep`） | Identity-H 靠 CID 当字形索引用；**浏览器走 Unicode 路径，没 cmap 就画不出** |
| ③ 补「码位=字形序号」的合成 cmap | 用 FreeType 逐码位渲染：`c=5→们`（应为「最」）、`c=4→什`（应为「后」） | **码位 ≠ 字形序号**，合成映射对不上 |

> [!IMPORTANT] 这一条推翻了「内嵌字体就能救」的直觉
> PDF 里 `Encoding: /Identity-H`、无 `CIDToGIDMap`（按规范默认 Identity），
> 理论上 GID 应等于码位；但抽取出的字体里码位与字形序号并不对应，
> 说明需要从 PDF 编码结构重建 **CID→Unicode** 映射并改写文本
> —— 这正是 `pdf2htmlEX` 一类工具存在的理由。
>
> **对该文件的可行路径只有两条：OCR，或栅格化渲染。**

### 4.2 HTML 一律保不住的东西

- **PDF 非页面特性**：书签目录、批注/注释、表单域、图层（OCG）、内嵌附件 —— 三条路线全部丢失
- **精确定位与字体度量**：B/C 路线依赖字体度量一致，换字体就会位移
- **可访问性**：A 路线全是图片，屏幕阅读器读不到

### 4.3 还依赖本机字体（路线 B）

PyMuPDF 输出的 `font-family` 只写**名字**（`SimSun,serif` / `KaiTi,serif` / `DengXian,serif` / `SymbolMT,serif`），
**不内嵌字形**。本机是 Windows 且装了这些字体，所以看起来正常；
换到 Linux / macOS / 手机就可能字体替换、段落重排。**PDF 不会——PDF 把字体嵌在里面。**

## 五、可搜索性的对比

| 方案 | 全文搜索 | 复制文字 | 图形保真 | 单文件体积 |
| --- | --- | --- | --- | --- |
| 原始 PDF | ✅ | ✅ | ✅ | 1× |
| Markdown | ✅ | ✅ | ❌ | 0.02× |
| HTML · 栅格 | ❌ | ❌ | ✅ | 0.4–1.1× |
| HTML · 定位文字 | ✅ | ✅ | ✅ | 0.9–1.1× |
| HTML · 定位文字+字体 | ✅（除编码损坏件） | ✅ | ✅ | 1.0–1.1× |

## 六、对「删原件」这个决策意味着什么

渲染 HTML **不改变** [[topics/原件保留必要性评估]] 的结论：

1. **8 份零内容文件**（816 页 / 178.90 MB）：HTML 栅格化确实能把它们变成可视内容，
   但代价是体积不降反升，且**编码损坏那份即使栅格化了，文字仍不可检索**。
   真正的解法是 OCR 后补进 `markdown/`。
2. **其余文件**：HTML 的图形保真优于 Markdown，但**体积上没有收益**（127 MB 的低清栅格换来的是清晰度损失）。
3. **PDF 特性**（书签/批注/表单）任何 HTML 方案都保不住。
4. **仓库体积**不会因为换成 HTML 而减小——原件仍在 git 历史里。

> [!NOTE] 分工建议
> - **检索、跨资料综合** → 用本知识库的 `markdown/` + `wiki/`
> - **看图表、核对公式版式** → 回原件（或对关键页做栅格 HTML）
> - **要一个能脱离 PDF 阅读器分发的版本** → 栅格 HTML 可行，但要接受体积与不可搜索
> - **编码损坏 / 扫描件** → 先 OCR，别的路都绕不过去

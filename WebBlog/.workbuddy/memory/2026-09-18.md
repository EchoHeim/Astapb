### 4. 两个必须记录的技术坑
1. **Shiki 只配一套主题会让深色模式代码块变成"深底深字"**。
   必须 `themes: { light, dark }` + `defaultColor: false`，让 Shiki 输出
   `--shiki-light` / `--shiki-dark` 自定义属性，再由 CSS 按 `[data-theme]` 挑选。
   已核验：长文页 `--shiki-dark` 出现 5212 次、写死的 `style="color:#"` 为 **0**。
2. **`langAlias` 里不能写自映射**（如 `xml: 'xml'`、`dts: 'dts'`），
   Shiki 会报 `Circular alias`。本身就是正确小写的语言标记不要出现在别名表里。

### 5. Astro 7 的更多坑（补第十轮）
- `src/pages/*.json.js` **不支持 TypeScript 语法**，端点里写了类型标注会
  `PARSE_ERROR`。要用 `.ts` 后缀（`search-index.json.ts`）。
- 打包脚本里可以用 `import.meta.env.BASE_URL`；`<script is:inline>` 里不行，
  需要走 `define:vars` 或从 DOM 的 data 属性读。

### 6. 布局取舍（值得记，别再改回去）
目录侧栏**没有**用栅格，而是 `position: fixed` 定位到正文右侧空白区
（`left: calc(50% + 396px)`），仅在 **≥1200px** 出现。
原因：正文容器的 720px 是阅读最舒服的行宽，用栅格加一列会把正文压窄。
空间换算 = 720/2 + 208(目录) + 36(间距) → 视口至少 1200px。

### 7. 「md 会自动同步吗」的答案（用户第 3 问）
**会，而且现在是无条件的** —— 新增了 `scripts/sync-content.mjs`，挂在 npm 的
`prebuild` / `predev` 上，每次构建前自动：

  标签按目录推断、摘要取首段）；

## 第十三轮：诊断 verilog.md 图片全部丢失（用户截图提问）

用户贴出 `FPGA/verilog.md` 页面截图，配图位置全是破图占位。

### 结论：只有这一篇有问题，22 张图全坏，且**与站点迁移无关**
- 该文 22 张图的地址全部是
  `https://github.com/EchoHeim/KQ-Glue/assets/26021085/<uuid>` ——
  这是 **GitHub 仓库附件**地址（往 issue/PR 评论里拖拽上传的图），**不是仓库里的文件**。
- 实测 **22/22 全部 HTTP 404**；`api.github.com/repos/EchoHeim/KQ-Glue` 也返回 404
  （对照：`EchoHeim/Astapb` 返回 200 public）。
  匿名 404 无法区分「仓库已删」与「仓库私有」—— **私有仓库的附件只对登录且有权限的人可见**。
- **与渲染方式无关**：Markdown 里就是这个 URL，docsify 与 Astro 都只是把它原样写进
  `<img src>`。旧站点上这些图**同样是坏的**，换框架不会改变。
- 推翻过一个假设：曾怀疑是 GitHub 改了附件地址格式（`/<owner>/<repo>/assets/<id>/<uuid>`
  → `/user-attachments/assets/<uuid>`），实测新格式同样 404，**不是地址格式问题**。

### 其余文章配图是好的（重要，别误报）
全库扫描后 **95 张图 / 25 篇文章** 用的是旧的
`https://user-images.githubusercontent.com/...` 托管，**全部存活**（抽样 8/8 返回
200 + `image/png` + 真实 PNG 字节头）。

### 教训：URL 正则不要截断扩展名
我第一轮扫描用的正则 `user-images\.githubusercontent\.com/[0-9]+/[0-9a-f-]+`
在 `.png` 前停住，导致拿掉扩展名去请求 → **全部 403**，差点报出「25 篇文章的图都坏了」
的错误结论。补上 `\.[a-z]{3,4}` 后全是 200。
**判断远程资源存活，必须用与原文完全一致的地址去请求**，不能用自己裁剪过的版本。

### 顺带确认的事实
`github.com/<owner>/<repo>/assets/<user_id>/<uuid>` 这类地址的可用性
**取决于源仓库的可访问性**，与图片本身是否还在无关。
所以引用 GitHub 附件做图床有硬伤：仓库一改权限或删除，文章配图立即全灭 ——
**图片应该进仓库或独立资源仓库（jsDelivr），而不是引用 issue 附件**。
